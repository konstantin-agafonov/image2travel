# 12. Парсинг расписаний, цен, ограничений и погоды

[Оглавление](README.md) · Далее: [конвейер](13-ingestion-pipeline.md)

## 1. Официальные страницы операторов

Реестр для каждого POI содержит конкретные URL оператора/парка, разрешённый способ получения и parser version. Нет универсального «найди сайт и распарсь всё».

Приоритет получения: документированный API/CSV → JSON-LD → разрешённые HTML-таблицы → ручной ввод со ссылкой. Если сайт требует JS, CAPTCHA, логин или запрещает сбор, для MVP выбрать ручную проверку; браузер не используется для обхода.

### Обработка

1. HTTP fetch с allowlist, лимитом размера/времени, User-Agent и условными ETag/Last-Modified-заголовками.
2. Найти документированные JSON-поля, `openingHoursSpecification`/Offer в JSON-LD либо заданные CSS-selectors. Проверить, к какому объекту относятся данные.
3. Извлечь исходный текст, язык, период действия, цену/валюту, audience, включённые сборы и исключения.
4. Нормализовать числа с учётом десятичного разделителя, денежного номинала и единицы оплаты. «От €20» не превращать в верхнюю границу €20.
5. Расписание разобрать в локальной timezone: дни недели, интервалы, ночные часы, сезон, праздники, последний вход и конкретные закрытия.
6. Неизвестную оговорку оставить `partial`; критичные цены/закрытия проходят ручное review при первом импорте и изменении.
7. Создать claims с locator, revision/hash и условиями действия; publisher обновляет pois/price_estimates/access_rules.

Сломанный selector или исчезнувшая таблица — `parser_drift` и review. Не обнулять цены и не ставить `24/7` при пустом ответе. Данные JSON-LD могут быть устаревшими: сверять явный тариф/расписание страницы и отмечать конфликт.

## 2. Въезд и advisories

Выбирать реестр страниц компетентных органов **для выбранных стран**, а не единый глобальный parser. RSS/API предпочтительнее HTML при наличии и разрешении. Парсер извлекает issuer, регион, уровень/формулировку, дату обновления, условия гражданства, срок и исключения.

Редактор сопоставляет формулировки с `info/caution/avoid` по документированной методике. Требование визы нельзя вывести из advisory о безопасности. Автоматическое изменение страны на «разрешён въезд» не допускается без review; отрицательные подтверждённые ограничения могут срочно блокировать выдачу.

Куда: travel_restrictions + claims/evidence. Unknown coverage и устаревший источник возвращаются в MCP как «нужна проверка», особенно до бронирования.

## 3. Климатическая статистика

Источник: Open-Meteo Historical Weather API `/v1/archive`. Для каждой базы направления запросить выбранный воспроизводимый период, например 1991–2020, если dataset его покрывает. Доступность периода и переменных проверить перед импортом.

```text
https://archive-api.open-meteo.com/v1/archive
  ?latitude=46.36&longitude=14.09
  &start_date=1991-01-01&end_date=2020-12-31
  &daily=temperature_2m_mean,precipitation_sum
  &timezone=Europe%2FLjubljana
```

Разбивать большие запросы по годам в пределах условий провайдера. Проверять длины time/values, единицы, missing/null и полноту. Для каждого месяца усреднять месячные показатели по годам: сумму осадков, среднюю температуру, число дней с осадками ≥ 1 мм. Не усреднять дневные миллиметры как месячную сумму.

Записывать climate_months с dataset, периодом, sample_years, computed_at и derived claim. Недостаточные годы исключать/маркировать; исторические данные не объявлять вероятностью тумана без отдельной модели. В горах климат базы не гарантирует погоду на вершине.

## 4. Прогноз и свет

Open-Meteo `/v1/forecast`: координаты выбранных точек, даты в горизонте модели, температура, ветер, осадки, sunrise/sunset. Документация допускает до 16 дней в зависимости от модели; более дальние даты — только климатическая статистика.

Сохранять requested coordinates и фактическую grid-cell coordinate, timezone, единицы, время получения. Для переходов DST запрашивать Unix timestamps, преобразовывать через `zoneinfo`; фиксированного UTC-offset ответа недостаточно для всей поездки.

Куда: api_cache с TTL 1–6 часов и атрибуцией Open-Meteo. Рассвет/закат можно вычислять локально астрономической библиотекой на любую дату; полярный день/ночь и горизонт гор требуют отдельной обработки. Время рассвета не означает гарантированный свет/доступ.

## 5. Время наземных переездов

OSRM route/table по координатам доступа, не центрам озёр:

```text
{configured_base}/table/v1/{supported_profile}/{lon1},{lat1};{lon2},{lat2}
  ?annotations=duration,distance
```

Профиль определяется подготовленным графом сервера. Подстановка слова `foot` в URL автомобильного endpoint **не создаёт пешую маршрутизацию**. Для MVP использовать провайдера с подтверждённым профилем либо ручные проверенные длительности троп. При отсутствии профиля — unknown/estimated, не точный ETA.

Проверять `code`, null/NoRoute, snapping-distance и data_version. Duration — секунды, distance — метры; перевести в минуты с округлением вверх и отдельным буфером. Матрица не обязательно симметрична. Оценка по прямой линии допустима только как явно помеченная нижняя/грубая оценка, не доказательство доступной тропы через гору/воду.

Куда: api_cache, затем блоки transfer в Itinerary с методом и источником. Demo-сервер не считать сервисом с SLA. Полноценное общественное расписание требует GTFS/провайдера и переносится после MVP; без него дать ссылки на перевозчика и manual check.

## 6. Курсы валют

ECB: XML `https://www.ecb.europa.eu/stats/eurofxref/eurofxref-daily.xml`, дата в Cube/time, rate каждой currency к EUR. Для отсутствующей валюты не брать нулевой rate.

ЦБ РФ: `https://www.cbr.ru/scripts/XML_daily.asp`; читать CharCode, Nominal, Value, Date. Курс — Value/Nominal рублей за единицу, десятичную запятую преобразовать в Decimal. RUB→X — обратный курс, X→Y — кросс-курс с совместимой датой и явно названным методом.

Куда: currencies, exchange_rates и sources. XML-парсер без внешних сущностей/DTD. Выходные и праздники — последняя опубликованная дата, не «курс сегодняшнего дня». Справочный rate отличается от банковского обмена; добавить оговорку/резерв. ECB endpoint в текущей среде дал таймаут — доступность проверить при реализации.

## 7. Диапазоны бюджета

Без договорного API жилья — редакционная выборка **разрешённых официальных тарифов** нескольких вариантов на одну категорию/сезон. Хранить число примеров, даты, occupancy, диапазон и метод. Если примеров недостаточно, estimate с низкой уверенностью, а не «рыночная медиана».

Еда/транспорт — официальные меню и тарифы, доступные на разрешённых страницах, либо ручная оценка со ссылками. Обновление API в runtime не публикует автоматически новую базовую стоимость всего региона.
