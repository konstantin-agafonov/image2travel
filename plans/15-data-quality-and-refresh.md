# 15. Качество, дедупликация и обновление данных

[Оглавление](README.md) · Далее: [подбор](16-destination-matching.md)

## Свежесть зависит от поля

| Группа | Плановый срок перепроверки | Что делать после истечения |
|---|---|---|
| География, aliases, external IDs | 30–90 дней | Справка может быть stale; критичную точку доступа проверить |
| Часы работы | До 30 дней, чаще при сезонной смене | Не обещать точное открытие; manual check |
| Тарифы билетов | 7–30 дней и по периоду действия | Диапазон/старый тариф с предупреждением либо unknown |
| Жильё и бюджет на месте | До 30 дней для сезонной выборки | Только estimated, без наличия |
| Safety advisories | 24 часа для рискованной географии, до 7 дней для остальной | Не подтверждать безопасность; критичный маршрут needs_review/block |
| Въезд | До 7 дней и при изменениях | Обязательная проверка перед бронью, не «виза не нужна» |
| Временные закрытия парков | 24 часа при активном предупреждении | Закрытие не считать снятым только из-за TTL |
| Климатическая статистика | Ежегодно/при смене dataset | Сохранять период, не подменять прогнозом |
| Редакционный experience/crowd | 90–180 дней + сезонные изменения | Пометка editorial/stale, уточнить уверенность |
| FX | Новая публикация/рабочий день | Показывать фактическую дату; не выдумывать курс выходного |

Это внутренние целевые сроки, не обещание uptime источников. `review_due_at` — дата очередной проверки; `valid_to` — срок действия факта. Они различаются. TTL не превращает подтверждённый запрет в разрешение.

## Runtime-кэш

Прогноз: 1–6 часов; маршруты: до 7 дней с profile/data_version; геокодинг при разрешении: до 30 дней; справочники API: до 30 дней; FX: 24 часа с учётом календаря публикации. Отрицательный/ошибочный результат кэшировать коротко (например, минуты), не как успешный факт на месяц.

Stale fallback допустим для некритичной оценки с датой и статусом. Для опасного доступа/въезда устаревшее подтверждение не даёт зелёный статус. При большом TTL всё равно повторно проверять критичные сведения перед поездкой.

## Дедупликация

1. Точное совпадение внешнего ID — тот же объект, кроме явно расследуемого ошибочного ID.
2. Совпадение QID и совместимого типа — сильный сигнал; ссылку проверять.
3. Без ID использовать нормализованное название, категорию, близость координат, официальный домен и адрес.
4. Порог расстояния зависит от типа: кафе/вход — десятки метров, природная зона — другая геометрия. Нет универсального «в пределах 500 м значит одно место».
5. Различать объект, вход, тропу и viewpoint. Близкие точки могут давать разный доступ и впечатление.
6. Неоднозначное совпадение — review, не автоматический merge по fuzzy name.

Merge сохраняет исходные external IDs/evidence и переназначает связи транзакционно. Канонический ID сохраняется, второй entity retired; историю не удалять. Не сливать частные/чувствительные точки в публичный объект без проверки.

## Конфликт источников

Приоритет **по полю**, не универсальный рейтинг сайта:

- Координаты/идентичность: сопоставление OSM/Wikidata и типа объекта; официальный вход для маршрута важнее центра полигона.
- Расписание/тариф/закрытие: актуальный компетентный оператор с подходящим сезоном/аудиторией предпочтительнее старого гида.
- Въезд: органы назначения и применимые условия, не блог.
- Безопасность: компетентные advisories с issuer/региональным scope; несовместимые рекомендации не усреднять в «безопасно».
- Эмоции/длительность/crowd: редакционные оценки, а не подтверждённые объективные свойства.

Сначала проверить даты, валюту, audience, период и точку. Две разные цены могут относиться к детям/взрослым или сезонам и не конфликтовать. Неразрешённый конфликт создаёт current claim `conflicting`, предупреждение и запрет уверенной публикации критичного значения.

## Автоматические проверки перед публикацией

- Уникальные IDs, действительные FK, entity kind, диапазоны координат и месяц 1–12.
- JSON валиден и соответствует Pydantic-схеме; timezone из IANA; числа/валюты/единицы согласованы.
- Цена high ≥ low, basis известен, occupancy там, где требуется.
- Source-origin verified claim имеет supports evidence; checked_at не в будущем; parser version зафиксирована.
- У каждого критичного projected field есть current claim правильного статуса/периода.
- Claim field_path не ссылается на отсутствующее правило/цену; dependency graph ацикличен.
- Координата маршрута — точка/вход; representative/unknown не выдаётся как гарантированный вход.
- Кандидаты вне региона, absurd duration и незнакомая категория — review.
- FTS синхронизирован после изменения имени/тегов/алиасов; `foreign_key_check` и `integrity_check` проходят.

## Обновление без отдельной инфраструктуры

Оператор запускает `ingest --refresh-due`, смотрит dry-run diff и review. Можно использовать внешний timer, не добавляя очередь в MVP. Обновления seeds проходят git review; свежие runtime-проверки — запись provenance и бэкап.

Отчёт: coverage по направлениям и критичным полям, доля unknown/stale/conflicting, parser drift, pending review, изменения active POI, расход лимитов. Ошибка обновления меняет last_attempt, но **не checked_at/last_success** и не уничтожает старые свидетельства.
