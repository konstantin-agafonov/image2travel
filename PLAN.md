# Image2Travel — план ИИ-агента (MCP-first)

> **Задача:** пользователь загружает изображение и получает план путешествия, который поможет пережить впечатления, стоящие за этим изображением.
>
> **Ключевой принцип:** агент подбирает не «место, похожее по картинке», а **набор ощущений и условий**, которые создают это впечатление: свет, масштаб, тишину, ритм, активность, еду, людей вокруг и сезон.
>
> **Формат MVP:** **skill + MCP-сервер** на SQLite, с локальными файлами и запуском через `docker compose up`. Пользователь работает в своём AI-агенте (Claude, ChatGPT, Cursor, OpenCode), а не в отдельном веб-приложении.

## 1. Резюме

### Что делает продукт

1. Принимает фотографию и, при желании, короткий текстовый контекст.
2. Разбирает изображение на «слои впечатления»: что видно, что это за место, почему оно цепляет и что в этом опыте нельзя потерять.
3. Предлагает 2–3 направления: точное место (если оно определяется), «такой же вайб, но дешевле/ближе/менее людно» и неожиданную альтернативу.
4. Собирает реалистичный маршрут: дни, время, перемещения, бюджет, сезон, бронирования и запасные варианты.
5. Прозрачно показывает уверенность, источники и допущения.

### Главная гипотеза MVP

Пользователю не нужна энциклопедия достопримечательностей. Ему нужен **перевод изображения в конкретный, желанный и выполнимый план поездки**. Первая версия должна проверить не качество распознавания landmarks, а качество связки:

**«увидел фото → понял, что именно хочу пережить → получил маршрут, которому верю»**

Дополнительная гипотеза MCP-first: **агент пользователя уже умеет видеть фото, вести диалог и вызывать инструменты**. Нам достаточно дать ему качественные данные, расчёты и инструкцию — не нужно строить собственный чат, оркестратор и фронтенд.

### Что не обещаем

- «Точно такие же» впечатления: впечатление зависит от погоды, сезона, настроения и самого путешественника.
- Гарантированное распознавание любого места.
- Точные цены, наличие билетов и визовые гарантии без проверки в реальном времени.
- Одинаковое качество во всех host-агентах: оно зависит от модели, vision и дисциплины вызова tools.

Вместо этого обещаем: **понятную интерпретацию, обоснованные альтернативы и честные ограничения**.

### Главное изменение концепции

Вместо собственного оркестратора, базы PostgreSQL, Redis, S3, очередей и фронтенда:

| Было | Стало |
|---|---|
| Orchestrator + state machine | Host-агент + skill |
| Image Interpreter | Мультимодальная LLM host-агента |
| Clarifier | Host-агент + правила в skill |
| Presenter | Host-агент; текст и Markdown |
| PostgreSQL + pgvector | SQLite + FTS5 |
| Redis | Таблица `api_cache` в SQLite |
| S3 | Локальная папка `data/files/` |
| Celery/RQ | Синхронные tools с таймаутом |
| Next.js + интерактивные карты + auth | Чат host-агента; auth не нужен в MVP |
| Отдельный backend + инфраструктура | Один контейнер + SQLite + `./data` |
| PDF-пайплайн | Markdown, `.ics`, GeoJSON |
| MCP App | Next steps, после проверки текстового сценария |

## 2. Пользовательский сценарий

### Основной путь

1. **Загрузка.** Пользователь открывает своего AI-агента, загружает одно фото (JPG/PNG/HEIC, до 15 МБ) и может добавить комментарий: «хочу так же», «это медовый месяц», «с детьми», «бюджетно».
2. **Интерпретация.** Агент показывает короткое резюме:
   > «Это тихое горное утро: туман над водой, хвойный лес, рассветный свет и почти нет людей. Главное здесь — не озеро само по себе, а медленный ритуал раннего подъёма и ощущение уединения».
3. **Уточнения.** Агент задаёт **не более трёх** вопросов, только если без них план будет заметно хуже:
   - откуда и когда едем;
   - сколько дней и какой бюджет;
   - важнее повторить место или получить похожее впечатление.
4. **Быстрый путь.** Если пользователь не хочет отвечать, агент строит план по разумным допущениям и явно их показывает.
5. **Варианты.** Пользователь получает три концепции направления с объяснением, чем они отличаются.
6. **Маршрут.** Выбирает вариант → получает детальный план по дням, смету, ссылки и «инструкцию по впечатлению».
7. **Итерация.** Может попросить: «дешевле», «меньше людей», «больше природы», «добавь гастрономию», «только 5 дней».
8. **Экспорт.** Получает Markdown, `.ics` или GeoJSON. PDF и интерактивная карта — в next steps.

### Принципы диалога

- Не спрашивать то, что можно аккуратно вывести из изображения или разумно предположить.
- Не заваливать анкетой: сначала ценность, потом уточнения.
- Всегда отделять **факт** («это озеро Блед») от **интерпретации** («здесь ценят тишину») и **рекомендации** («приезжайте к 6:30»).
- Давать пользователю управлять балансом: «точное место ↔ похожее впечатление», «бюджет ↔ комфорт», «популярное ↔ неизбитое».
- Если агент не уверен — говорить «похоже на», а не выдавать догадку за факт.

### Где живёт пользовательский интерфейс

В MVP интерфейс — это чат host-агента. Он умеет показывать текст, изображения, ссылки и таблицы. Наш MCP-сервер не рисует UI и не хранит диалог.

Если у пользователя нет агента с MCP, это не целевой пользователь MVP. Веб-приложение для массового потребителя — отдельный next step, который переиспользует тот же Python-core.

## 3. Что агент должен извлечь из изображения

### Слои анализа

| Слой | Что извлекаем | Пример |
|---|---|---|
| Сцена | Объекты, ландшафт, архитектура, интерьер | озеро, ели, туман, деревянный причал |
| География | Страна/регион/конкретная точка, если определяется | озеро в Альпах, вероятность 0.8 |
| Свет и время | Рассвет/закат, направление света, время суток | мягкий рассветный свет, тени длинные |
| Сезон и погода | По листве, снегу, одежде, цвету | поздняя весна, прохладное утро |
| Активность | Что делают или могут делать люди | хайкинг, лодка, кофе на террасе |
| Сенсорика | Звук, температура, запахи, тактильность | тишина, прохлада, запах хвои |
| Социальность | Людность, приватность, формат компании | уединённо; пара или соло |
| Темп и усилие | Медленно/насыщенно, легко/поход | медленный ритуал, лёгкая прогулка |
| Эмоция | Главные чувства | покой, благоговение, ностальгия |
| Визуальный стиль | Палитра, контраст, композиция, текстуры | холодные синие тона, минимализм |
| Культурные маркеры | Еда, одежда, традиции, музыка | традиционный завтрак, рынок |

### Experience Fingerprint

Ключевой артефакт — структурированный «отпечаток впечатления». Он позволяет сравнивать места не только по визуальной похожести, но и по опыту.

```json
{
  "summary": "Тихое горное утро у воды",
  "visible_facts": [
    "озеро",
    "хвойный лес",
    "туман над водой",
    "рассветный свет"
  ],
  "inferred": {
    "season": "поздняя весна",
    "time_of_day": "рассвет",
    "weather": "прохладно, без ветра",
    "crowd_level": "низкая"
  },
  "experience": {
    "emotions": ["покой", "уединение", "благоговение"],
    "pace": "медленный",
    "effort": "лёгкая прогулка",
    "social": "приватно",
    "sensory": {
      "sight": ["мягкий свет", "большое пространство"],
      "sound": ["тишина", "вода"],
      "smell": ["хвоя", "влажный воздух"],
      "temperature": "прохладно"
    }
  },
  "must_preserve": [
    "вода и туман на рассвете",
    "отсутствие толпы",
    "короткий путь до уединённой точки",
    "медленный завтрак после прогулки"
  ],
  "nice_to_have": ["деревянный причал", "горный вид из окна"],
  "avoid": ["курортные комплексы", "шумные экскурсии"],
  "location": {
    "candidate": "озеро в Альпах",
    "confidence": 0.82,
    "evidence": ["характерный силуэт", "растительность", "архитектура причала"],
    "needs_verification": true
  },
  "clarify": ["даты", "бюджет", "готовность к перелёту"]
}
```

### Trip Brief

Fingerprint описывает впечатление. Для подбора нужны ещё практические ограничения. Вместе они образуют `TripBrief` — единственный вход для `plan_trip`.

```json
{
  "fingerprint": {
    "summary": "тихое горное утро у воды",
    "emotions": ["покой", "уединение"],
    "pace": "медленный",
    "crowd": "низкая",
    "season": "поздняя весна",
    "must_preserve": ["вода и туман на рассвете", "мало людей"]
  },
  "constraints": {
    "origin": "Москва",
    "start_date": "2026-05-10",
    "days": 5,
    "budget_usd": 1200,
    "mode": "twin"
  }
}
```

`mode`:

- **Exact** — место определено с высокой уверенностью и подтверждено независимыми источниками. План строится вокруг него.
- **Twin** — место не определено или оно недоступно/перегружено. Подбираются направления с тем же «отпечатком».
- **Wildcard** — сохраняется эмоция, но меняется декорация.

Правило: если уверенность ниже порога, **не выдавать догадку за факт**. Формулировка: «Похоже на X, но подтвердить нельзя. Вот что важно сохранить, и вот три места, где это можно пережить».

## 4. Архитектура: Skill + MCP + SQLite + локальные файлы

### Общая схема

```text
Пользователь
   │ фото + контекст
   ▼
Host-агент (Claude / ChatGPT / Cursor / OpenCode / Codex)
   ├── Skill: как анализировать, что спрашивать, как отвечать
   ├── Мозг: мультимодальная LLM
   └── MCP client
         │ JSON tools
         ▼
MCP-сервер (Python + FastMCP)
   ├── plan_trip
   ├── get_destination
   ├── build_itinerary
   ├── validate_itinerary
   ├── verify_place
   └── export_itinerary
         │
         ├── SQLite: data/image2travel.db
         ├── Файлы: data/files/
         └── Внешние API: OSM/OSRM, Open-Meteo, опционально рейсы
```

MCP App, интерактивные карты и PDF **не входят в MVP**. Они появляются в next steps, когда текстовый сценарий доказал качество.

### Разделение ответственности

| Роль | Где живёт | Что делает |
|---|---|---|
| Понимание изображения | Host-агент | Видит фото, извлекает сцену, эмоции, сезон, людность |
| Experience Fingerprint | Host + skill | Заполняет структуру по схеме |
| Уточнения | Host + skill | Задаёт максимум 3 вопроса, применяет defaults |
| Подбор направлений | MCP-сервер | Жёсткие фильтры, скоринг, диверсификация |
| Проверка места | MCP-сервер | OSM/Wikidata/Wikipedia, confidence, источники |
| Маршрут | MCP-сервер | Детерминированный скелет по дням |
| Валидация | MCP-сервер | Переезды, часы работы, сезон, бюджет |
| Финальный текст | Host-агент | Объясняет выбор, trade-offs, инструкцию по впечатлению |
| Хранение | SQLite + диск | Направления, точки, источники, кэш, файлы |
| UI | Чат host-агента | Текст, Markdown, ссылки; MCP App — позже |

### Почему не один большой промпт

- **Надёжность:** модель не удержит в контексте 50 направлений, 500 точек и все часы работы без ошибок.
- **Галлюцинации:** цены, расстояния и часы работы должны приходить из данных, а не из «памяти» модели.
- **Стоимость:** большой промпт с базой дороже, чем tool call с компактным ответом.
- **Обновляемость:** данные меняются, а промпт — нет.
- **Тестируемость:** функции подбора и валидации можно проверить без AI.
- **Переносимость:** один MCP-сервер работает в разных host-агентах.

### Почему MCP, а не только skill или CLI

| Вариант | Роль |
|---|---|
| **MCP + Skill** | Основной формат MVP |
| **CLI** | Dev-инструмент и fallback для агентов без MCP |
| **HTTP/OpenAPI** | Будущее веб-приложение на том же core |
| **A2A** | Не нужен на этом этапе |

Skill не даёт живые данные и воспроизводимые расчёты. CLI не работает в ChatGPT/Claude web. HTTP/OpenAPI требует отдельной интеграции под каждого клиента. MCP — самый короткий путь к большинству агентов.

### Транспорты

Один и тот же сервер поддерживает два режима:

- **stdio** — host запускает процесс локально. Подходит для Claude Desktop, Cursor, OpenCode, Codex. Приватно, не нужен хостинг.
- **Streamable HTTP** — сервер работает по URL. Подходит для ChatGPT, Claude web, нескольких пользователей. Нужен HTTPS и лимиты.

Docker Compose в MVP поднимает HTTP-версию. Для локального stdio можно использовать `uvx image2travel-mcp` или `docker compose run --rm -T image2travel ...`.

## 5. MCP-сервер

### Принципы

1. **В MVP сервер не вызывает LLM.** Он получает структурированный `TripBrief` и возвращает структурированный результат. Server-side vision — отдельный опциональный режим в next steps.
2. **Сервер не хранит пользовательскую сессию.** Состояние — это диалог host-агента. Сервер можно перезапускать между вызовами.
3. **Один высокий tool вместо десяти примитивов.** `plan_trip` надёжнее, чем `search → filter → rank → diversify → explain`.
4. **Компактные ответы.** Сначала 3 карточки с ID, потом детали по запросу. Не отправлять всю базу в контекст.
5. **Понятные ошибки.** Если входные данные неполные, вернуть `questions` и `assumptions`, а не падать.
6. **Все факты — с источником и датой.** Если источника нет, пометить как оценку.

### Tools

| Tool | Вход | Выход | Назначение |
|---|---|---|---|
| `plan_trip` | `TripBrief` | `PlanProposal`: 3 концепции, assumptions, questions, confidence | Главный сценарий подбора |
| `get_destination` | `destination_id`, опционально `month` | `DestinationCard` + источники | Детали выбранного направления |
| `build_itinerary` | `TripBrief`, `destination_id` | `Itinerary`: дни, точки, логистика, бюджет, план B | Детерминированный скелет маршрута |
| `validate_itinerary` | `Itinerary` | `ValidationReport`: ошибки, предупреждения, feasibility score | Проверка выполнимости |
| `verify_place` | `query` (название или координаты) | `PlaceMatch[]` + confidence + sources | Проверка точного места |
| `export_itinerary` | `Itinerary`, `format` | Контент + `file_id` | Markdown, `.ics`, GeoJSON |

Для самого быстрого прототипа достаточно трёх tools: `plan_trip`, `build_itinerary`, `validate_itinerary`. Остальные три — утилиты, которые добавляются на второй неделе.

`plan_trip` делает:

1. Валидацию `TripBrief` по схеме.
2. Жёсткие фильтры: даты, бюджет, визы, безопасность, сезон, время в пути.
3. Скоринг оставшихся направлений.
4. Диверсификацию (MMR-подобный отбор), чтобы не вернуть три клона.
5. Назначение ролей `exact` / `twin` / `wildcard`.
6. Объяснение: почему подходит, что теряется, где данных не хватает.

`build_itinerary` не пишет прозу. Он собирает структуру:

- группирует точки по районам;
- ставит 2–4 якорных впечатления в день;
- подбирает время суток;
- добавляет буферы и трансферы;
- проверяет часы работы и сезон;
- считает бюджет по категориям;
- добавляет план B.

`validate_itinerary` проверяет:

- невозможные переезды;
- закрытые места и сезонные ограничения;
- выход за бюджет;
- несоответствие темпа и количества точек;
- отсутствие источников у критичных фактов.

### Resources

- `image2travel://schemas/experience-fingerprint`
- `image2travel://schemas/trip-brief`
- `image2travel://schemas/itinerary`
- `image2travel://destinations/{id}`
- `image2travel://sources/{id}`
- `image2travel://files/{id}`
- `image2travel://methodology`

Resources нужны, чтобы host мог подгрузить схему или карточку без вызова tool. Это удобно, но не обязательно: основной путь работает через tools.

### Prompts

- `plan_from_photo` — пошаговый сценарий от фото до плана.
- `refine_plan` — «дешевле», «тише», «короче».
- `explain_tradeoffs` — сравнение трёх вариантов.

Prompts поддерживаются не всеми host. Поэтому основной workflow живёт в skill, а prompts — запасной вариант.

### Statelessness и состояние

В MVP сервер не хранит пользовательские поездки. Host передаёт `TripBrief` и выбранный `destination_id` при каждом вызове. Это даёт:

- простой рестарт контейнера;
- отсутствие миграций пользовательских данных;
- лёгкое тестирование;
- приватность.

SQLite хранит только справочники, кэш внешних API и метаданные файлов. Сохранённые поездки и аккаунты — next steps.

## 6. Skill

### Что это

Skill — это папка с `SKILL.md` и вспомогательными материалами. Это **инструкция для host-модели**, а не исполняемый код. Host подгружает её, когда пользователь просит спланировать поездку по фото.

Минимальный frontmatter:

```yaml
---
name: image2travel
description: Превращает фото путешествия в реалистичный план поездки с помощью MCP-сервера image2travel.
---
```

### Структура

```text
skill/
  SKILL.md
  references/
    experience-fingerprint.md
    output-template.md
    examples.md
```

Или, если skill живёт прямо в репозитории:

```text
.agents/skills/image2travel/
  SKILL.md
  references/
```

### Что внутри `SKILL.md`

1. **Когда использовать skill.**
2. **Роль и границы:** агент — планировщик впечатлений, а не туроператор и не гарант цен.
3. **Workflow:**
   - посмотреть фото;
   - собрать `Experience Fingerprint`;
   - проверить, хватает ли данных;
   - задать максимум 3 вопроса;
   - вызвать `plan_trip`;
   - показать 3 концепции;
   - после выбора вызвать `build_itinerary`;
   - вызвать `validate_itinerary`;
   - написать финальный ответ.
4. **Схема fingerprint и контролируемый словарь** для эмоций, темпа, людности, сезона.
5. **Политика вопросов:** что спрашивать, что предполагать, как показывать допущения.
6. **Политика честности:** факт vs интерпретация vs рекомендация; что делать при низкой уверенности.
7. **Формат ответа:** структура карточек, маршрута, сметы, практики и прозрачности.
8. **Правила вызова tools:** когда `plan_trip`, когда `get_destination`, когда `verify_place`.
9. **Примеры хорошего и плохого поведения.**
10. **Ограничения:** не бронировать, не оплачивать, не обещать визу, не выдумывать часы работы.

### Зачем skill, если есть MCP

- MCP говорит «какие инструменты есть», skill говорит «как делать работу хорошо».
- Описания tools должны быть короткими, а skill может быть длинным и нюансным.
- Skill версионируется вместе с сервером и ревьюится в git.
- Некоторые host поддерживают skills, но не поддерживают MCP prompts.
- Skill задаёт тон, структуру ответа и правила честности — это продукт, а не техническая обвязка.

### Установка и версионирование

- В репозитории: `.agents/skills/image2travel/SKILL.md`.
- В пакете: `skill/SKILL.md`, чтобы можно было установить одной командой.
- Skill устанавливается в host отдельно; контейнер содержит его копию для версии и документации, но не «пробрасывает» его агенту автоматически.
- Версия skill и версия MCP-сервера должны быть совместимы; в `SKILL.md` указать `server_version`.
- При изменении схемы `TripBrief` или имён tools обновлять skill и eval-набор.

## 7. Данные: SQLite и локальные файлы

### Принцип

**SQLite — единственная runtime-база.** Никаких PostgreSQL, pgvector и Redis в MVP.

Для удобного ревью первичные данные можно держать в YAML/JSON и загружать в SQLite идемпотентным seed-скриптом. После загрузки сервер читает только SQLite.

### Схема

```sql
-- Направления
CREATE TABLE destinations (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  country TEXT,
  region TEXT,
  lat REAL,
  lon REAL,
  summary TEXT,
  tags TEXT,
  experience_json TEXT NOT NULL,
  visual_json TEXT,
  budget_json TEXT,
  accessibility_json TEXT,
  safety_json TEXT,
  anti_features_json TEXT,
  updated_at TEXT NOT NULL
);

-- Сезонность и людность по месяцам
CREATE TABLE destination_months (
  destination_id TEXT NOT NULL,
  month INTEGER NOT NULL,
  season_score REAL,
  crowd_score REAL,
  note TEXT,
  PRIMARY KEY (destination_id, month),
  FOREIGN KEY (destination_id) REFERENCES destinations(id)
);

-- Точки интереса
CREATE TABLE pois (
  id TEXT PRIMARY KEY,
  destination_id TEXT NOT NULL,
  name TEXT NOT NULL,
  lat REAL,
  lon REAL,
  category TEXT,
  tags_json TEXT,
  duration_min INTEGER,
  best_time TEXT,
  opening_hours TEXT,
  season_json TEXT,
  booking_url TEXT,
  FOREIGN KEY (destination_id) REFERENCES destinations(id)
);

-- Источники и даты проверки
CREATE TABLE sources (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  entity_type TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  url TEXT NOT NULL,
  title TEXT,
  checked_at TEXT NOT NULL
);

-- Кэш внешних API
CREATE TABLE api_cache (
  key TEXT PRIMARY KEY,
  value_json TEXT NOT NULL,
  expires_at TEXT NOT NULL
);

-- Метаданные файлов на диске
CREATE TABLE files (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  path TEXT NOT NULL,
  mime_type TEXT NOT NULL,
  size_bytes INTEGER NOT NULL,
  sha256 TEXT,
  created_at TEXT NOT NULL,
  expires_at TEXT
);

-- Полнотекстовый поиск по названиям и описаниям
CREATE VIRTUAL TABLE destinations_fts USING fts5(
  id, name, country, summary, tags
);
```

### Матчинг без pgvector

Для 30–50 направлений векторная база не нужна.

1. **Жёсткие фильтры** в SQL: даты, бюджет, виза, безопасность, сезон, время в пути.
2. **Скоринг в Python:** сравнение тегов эмоций, темпа, людности, сезона, бюджета, удобства, новизны и визуального профиля.
3. **Диверсификация:** MMR-подобный отбор, чтобы три варианта отличались.
4. **Объяснение:** для каждого варианта — топ причин и trade-offs.

Если позже понадобится семантический поиск, добавить `sqlite-vec` и хранить embeddings как BLOB. Это next step, не MVP.

### Seed-данные

- `data/seed/destinations/*.yaml` — 30–50 направлений.
- `data/seed/pois/*.yaml` — 10–15 точек на направление.
- `python -m image2travel.seed` — идемпотентная загрузка в SQLite.
- `data/seed/` хранится в git; `data/image2travel.db` — нет.

### Локальные файлы вместо S3

Всё лежит в `data/files/` рядом с приложением:

```text
data/
  image2travel.db
  files/
    exports/     # Markdown, .ics, GeoJSON
    uploads/     # только если включён server-side vision
    tmp/         # временные файлы
```

Правила:

- Имена файлов генерирует сервер (UUID), а не пользователь.
- Путь не принимается от пользователя: только `file_id` из SQLite.
- Проверять MIME, расширение и размер.
- Для загрузок — TTL и периодическая очистка.
- `data/` не отдаётся как статическая папка; доступ только через MCP resource или контролируемый endpoint.
- В Docker `./data` монтируется в `/app/data`.

### Кэш

`api_cache` заменяет Redis:

- ключ — нормализованный запрос;
- значение — JSON;
- TTL: погода 1–6 часов, геокодинг 30 дней, маршруты 7 дней, справочники 30 дней.
- При недоступности API вернуть «нет данных» и ссылку для ручной проверки.

### Бэкапы

- SQLite: `sqlite3 data/image2travel.db ".backup 'backup.db'"` или копия при остановленном контейнере.
- Файлы: `tar` на папку `data/files/`.
- В Docker — регулярный backup тома `./data`.
- Секреты и API-ключи — только в `.env`, не в базе и не в git.

| Задача | Инструменты/источники | Комментарий |
|---|---|---|
| Понимание изображения | Мультимодальная LLM host-агента | Основной анализ сцены и эмоций |

| Жильё | Ссылки на агрегаторы, без фиктивного наличия | Диапазоны, не бронирование |

| События | Eventbrite/Ticketmaster, опционально | Не в MVP |
| Безопасность | Официальные travel advisories | Обязательная проверка для рискованных направлений |
| Курсы валют | API банка/ЦБ | Для сметы |
| Еда и мероприятия | Обзоры, гиды, локальные источники | Не выдавать субъективное за факт |

### Требования к данным

- **Провенанс:** у каждого важного факта — источник и дата.
- **Свежесть:** цены — 7–30 дней, часы работы — 30 дней, безопасность — ежедневно/еженедельно.
- **Лицензии:** соблюдать ToS API и лицензии на контент; не скрейпить закрытые источники.
- **Кэш:** агрессивно кэшировать популярные направления и типовые запросы.
- **Отказоустойчивость:** если источник недоступен, показать «нет данных» и ссылку для ручной проверки.
- **Без выдумок:** если факт не подтверждён, помечать как оценку или не включать.

## 9. База знаний о впечатлениях

Это не просто каталог городов. Нужна база, где у направления есть «профиль впечатления»:

| Поле | Пример |
|---|---|
| Направление | Регион, город, природная зона |
| Сезонность | Лучшие месяцы, сезон дождей, праздники, закрытия |
| Визуальный профиль | Ландшафт, архитектура, палитра, свет |
| Эмоции | Покой, драйв, романтика, приключение, уединение |
| Активности | Хайкинг, гастрономия, купание, музеи, ночная жизнь |
| Темп | Размеренный / насыщенный |
| Людность | Туристическая загруженность по месяцам |
| Бюджет | Диапазон на день: жильё, еда, транспорт |
| Доступность | Сложность перелёта, виза, мобильность, инфраструктура |
| Безопасность | Актуальные ограничения и риски |
| «Анти-фичи» | Например: «в июле центр переполнен», «нужна машина» |
| Похожие направления | Twin-альтернативы по отпечатку |
| Источники | Ссылки и дата обновления |

**Почему это важно:** поиск только по эмбеддингам изображений даст визуальные клоны, но не обеспечит нужный сезон, бюджет и опыт. Нужен гибрид: структурированные поля + жёсткие фильтры + скоринг + диверсификация.

### Стартовый сегмент

Чтобы не распыляться, MVP фокусируется на одном сегменте:

> **Природные поездки на 3–7 дней для пар и соло-путешественников со средним бюджетом.**

Это упрощает данные, подбор и eval. Расширение на города, гастрономию и семьи — после беты.

## 10. Как выбирать направления

### Сначала отсекаем невозможное

Жёсткие фильтры:

- даты и длительность поездки;
- бюджет (нижняя и верхняя граница);
- визовые ограничения и паспорт;
- безопасность и актуальные advisories;
- доступность (мобильность, возраст, здоровье — только по желанию пользователя);
- максимально приемлемое время в пути;
- сезонная доступность (закрытые перевалы, не сезон, праздники).

### Затем ранжируем

Черновая формула для MVP:

```text
match =
  0.30 * experience_similarity
+ 0.20 * seasonal_fit
+ 0.15 * budget_fit
+ 0.10 * travel_convenience
+ 0.10 * personalization
+ 0.10 * novelty
+ 0.05 * visual_similarity
- crowd_penalty
- safety_penalty
- accessibility_penalty
```

Веса — гипотеза, их нужно калибровать на оценках пользователей. Важнее не точная формула, а объяснимость: агент должен уметь сказать, **почему** вариант подходит и **чем он хуже** остальных.

### Диверсификация

Нельзя выдавать три почти одинаковых варианта. Использовать MMR-подобный отбор: максимизировать релевантность и одновременно различие между вариантами.

### Три карточки на выходе

1. **Точное место** — если геолокация надёжна и поездка реалистична.
2. **Ближе/дешевле/тише** — тот же опыт с меньшими затратами или толпой.
3. **Смелая альтернатива** — та же эмоция в другой декорации.

У каждой карточки:

- почему это совпадение;
- что придётся потерять;
- лучший сезон;
- ориентировочный бюджет и время в пути;
- насколько людно;
- что может испортить впечатление;
- уверенность и допущения.

## 11. Генерация маршрута

### Логика планирования

1. Выбрать базу и районы, чтобы не тратить день на переезды.
2. Сгруппировать активности по географии и времени работы.
3. Поставить **2–4 якорных впечатления в день**, а не 10 галочек.
4. Подогнать время суток под опыт: рассвет — на рассвет, рынок — утром, закат — на закате.
5. Добавить буферы на дорогу и отдых.
6. Проверить открытие/закрытие, сезонность, праздники.
7. Предложить план B на случай дождя или усталости.
8. Посчитать бюджет по категориям и указать диапазоны.
9. Добавить «ритуалы впечатления»: ранний подъём, лодку, ужин без спешки, ночную прогулку.
10. Дать чек-лист бронирований и ссылки на проверку.

### Правила реалистичности

- Не ставить два удалённых места в один день без явного расчёта.
- Не игнорировать время на трансфер из аэропорта.
- Не советовать место, закрытое в выбранный сезон.
- Не обещать «тишину» в пик сезона — предупреждать и предлагать альтернативу.
- Не отправлять в опасные или закрытые зоны.
- Для природных мест учитывать правила парков, дронов, костров и поведения с животными.
- Не рекомендовать проникновение на частные территории ради «кадра».

### «Инструкция по впечатлению»

Отдельный блок ответа:

- откуда смотреть и в какое время;
- какая погода нужна для нужного света;
- сколько идти и что взять;
- как избежать толпы;
- как сделать похожий кадр (ракурс, объектив, штатив, разрешения);
- как не нарушить местные правила и не навредить природе;
- что делать, если погода не совпала.

## 12. Формат ответа пользователю

В MVP ответ — это **текст в чате host-агента**, а не отдельный экран. Внутри сервер возвращает структурированный JSON, host превращает его в понятный Markdown.

### 1. «Что вы на самом деле увидели»

Короткое объяснение впечатления: не «это озеро», а «это утро, в котором важны тишина, вода, свет и отсутствие спешки».

### 2. Три варианта направления

Карточки в тексте:

- название и регион;
- почему совпадает;
- что придётся потерять;
- сезон, бюджет, время в пути;
- людность;
- уверенность и допущения;
- ссылка на лицензированное изображение (опционально).

Кнопки и интерактивные карточки — MCP App в next steps.

### 3. Маршрут по дням

| День | Утро | День | Вечер | Логистика | План B |
|---|---|---|---|---|---|

Для каждого пункта: время, адрес/координаты, ссылка, стоимость, длительность, бронь, доступность.

### 4. Смета

- перелёт;
- жильё;
- транспорт;
- еда;
- входные билеты и активности;
- резерв 10–15 %.

С диапазонами, валютой и датой расчёта.

### 5. Практика

- виза и документы;
- сезон и одежда;
- страховка;
- местные правила;
- что бронировать заранее;
- меры безопасности;
- экологичный выбор.

### 6. Прозрачность

- что подтверждено источником;
- что является оценкой;
- где агент не уверен;
- какие допущения сделаны;
- когда данные последний раз обновлялись.

### Экспорт

- Markdown — основной формат;
- `.ics` — календарь;
- GeoJSON — точки для карты;
- PDF — next step;
- публичная ссылка — next step.

## 13. MVP

### Входит в первую версию

- Одно изображение + необязательный текст.
- Host-агент с vision и MCP; минимум 3 совместимых host.
- Skill с workflow, схемой и политикой честности.
- MCP-сервер на 6 tools.
- SQLite как единственная БД.
- 30–50 направлений в стартовом сегменте.
- Experience Fingerprint и `TripBrief`.
- До трёх уточняющих вопросов и «быстрый путь» с допущениями.
- Три концепции направления.
- Один детальный маршрут на 1–7 дней.
- Смета, ссылки, confidence.
- Правки в диалоге: дешевле, тише, короче, больше природы.
- Markdown/`.ics`/GeoJSON.
- Обратная связь с бетой: ручной CSAT и интервью; автоматический сбор — next step.
- Docker Compose: `docker compose up`.
- Локальные файлы в `data/files/`.
- Локальный stdio и удалённый HTTP.

### Не входит в MVP

- Собственный веб-интерфейс.
- MCP App и интерактивные карты.
- PDF и публичные ссылки.
- Аккаунты, OAuth, сохранённые поездки.
- PostgreSQL, pgvector, Redis, S3.
- Celery/RQ и фоновые очереди.
- Покупка билетов и оплата внутри продукта.
- Гарантия наличия и цен в реальном времени.
- Визовое сопровождение.
- Мультиизображение и групповая поездка.
- Офлайн-навигация.
- Точная геолокация частных и чувствительных мест.
- Server-side vision по умолчанию.

## 14. Docker Compose и запуск одной командой

### Принцип

Один сервис. Никаких отдельных контейнеров для БД, Redis и очередей. SQLite и файлы лежат в `./data` на хосте и монтируются в контейнер.

### `compose.yaml`

```yaml
services:
  image2travel:
    build: .
    ports:
      - "8000:8000"
    environment:
      IMAGE2TRAVEL_DATA: /app/data
      IMAGE2TRAVEL_HOST: 0.0.0.0
      IMAGE2TRAVEL_PORT: 8000
```

## 15. Метрики и оценка качества

### Golden set

Собрать 30–50 изображений для MVP, стратифицированных по категориям:

- известные landmarks;
- природа без landmarks;
- города, интерьеры, еда;
- ночные и зимние сцены;
- аэрофото и необычные ракурсы;
- изображения с людьми;
- неоднозначные и «неопределимые» фото;
- разные регионы и бюджеты.

Для каждого изображения — человеческая разметка: experience-теги, допустимые направления, «must preserve», сложность.

### Метрики

| Метрика | Что измеряет | Ориентир MVP |
|---|---|---|
| Location top-3 accuracy | Попадание точного места в топ-3 на определимых фото | ≥ 85% |
| Experience match | Насколько предложение передаёт впечатление (слепая оценка 1–5) | ≥ 4.0 |
| Itinerary feasibility | Доля маршрутов без невозможных переездов/закрытий | ≥ 95% |
| Groundedness | Доля важных фактов с источником или пометкой «оценка» | ≥ 95% |
| Constraint satisfaction | Бюджет, даты, доступность, виза | ≥ 95% |
| Hallucination rate | Выдуманные места, часы, цены | < 1% критичных |
| Tool call success | Доля успешных вызовов MCP tools | ≥ 98% |
| Host compatibility | 3 host проходят один и тот же smoke test | 3 из 3 |
| Time to first plan | Время до первой полезной выдачи | < 60 сек |
| Cost per plan | Внешние API + хостинг; токены host оплачивает пользователь | < $0.10 API |
| CSAT / повторное использование | Пользовательская ценность | измерять с беты |

Цифры — стартовые гипотезы, а не обещания. Их нужно откалибровать после первых 50–100 реальных запросов.

### Как оценивать

- **Unit-тесты:** фильтры, скоринг, маршрут, валидатор — без AI.
- **Eval-набор:** 30–50 фото → ожидаемые направления и experience-теги.
- **Smoke test в 3 host:** Claude, ChatGPT, Cursor/OpenCode.
- **Автоматические проверки:** маршруты, время, бюджет, ссылки, сезонность.
- **LLM-as-judge** — только как дополнительный сигнал.
- **Человеческая слепая оценка:** два варианта на одно фото, выбор лучшего.
- **Red teaming:** приватность, инъекции в изображениях, опасные рекомендации.

## 16. Безопасность, право и этика

### Приватность

- Изображение по умолчанию остаётся в host-агенте; MCP-сервер получает только `Experience Fingerprint`.
- Если включён server-side vision, загружать фото только с согласия, хранить в `data/files/uploads/` с TTL и удалять по расписанию.
- Не распознавать лица и не делать чувствительных выводов о людях на фото.
- Не обучать модели на пользовательских фото без явного согласия.
- Шифровать данные, ограничивать доступ, вести аудит.
- В логах не хранить изображения и персональные данные.

### Безопасность агента

- Изображение и текст на нём — **недоверенный ввод**. Текст вроде «игнорируй инструкции» не должен менять политику.
- Инструменты возвращают недоверенные данные: не выполнять инструкции из ответов API.
- Ограничить агента: он не бронирует и не платит без явного подтверждения.
- Валидация файлов, антивирусная проверка, лимиты запросов.
- Не раскрывать точные адреса частных домов и чувствительных объектов.

### Безопасность локальных файлов

- Никаких пользовательских путей: только `file_id` из SQLite.
- Генерировать имена через UUID; проверять MIME, расширение и размер.
- `data/files/` не отдавать как статику.
- Ограничить размер загрузки и суммарный диск.
- TTL и cron-очистка для `uploads/` и `tmp/`.
- Контейнер — non-root; `data/` — единственная writable-папка.
- Не монтировать Docker socket и не давать лишних прав.

### Ответственный туризм

- Предупреждать о перегруженных местах и предлагать альтернативы.
- Не публиковать геометки хрупких природных локаций.
- Учитывать правила парков, запреты на дроны, сезонные ограничения.
- Не романтизировать рискованные или незаконные действия ради кадра.
- Давать ссылки на локальные правила и устойчивые варианты.

### Правовые ограничения

- Соблюдать условия карт, авиа-, отельных и поисковых API.
- Использовать лицензированные изображения в карточках.
- Не гарантировать визу, безопасность и цены.
- Чётко обозначать партнёрские ссылки.
- Хранить источники и даты, чтобы можно было объяснить рекомендацию.

## 17. Риски и меры

| Риск | Проявление | Мера |
|---|---|---|
| Неверная геолокация | Агент уверенно называет не то место | `verify_place`, confidence, 2 источника, режим Twin |
| Галлюцинации | Выдуманные часы, цены, места | Tools, провенанс, даты, валидатор, «проверьте перед поездкой» |
| «Не те» впечатления | Пользователь ждал одно, получил другое | Разбор must preserve, объяснение trade-offs, обратная связь |
| Слишком общие советы | «Посетите Париж» | Experience fingerprint, конкретные районы, время, ритуалы |
| Перегруженность | Все едут в одно место | Crowd data, twin-альтернативы, сезонные предупреждения |
| Устаревшие данные | Закрытое кафе, изменившиеся цены | TTL, ссылки, ручная проверка критичного |
| Долгая генерация | Пользователь уходит | Preview, потоковые шаги, кэш |
| Дорогие API | План стоит больше выручки | Кэш, лимиты, дешёвые источники |
| Предвзятость | Только дорогие и раскрученные места | Диверсификация, бюджетные варианты, геобаланс |
| Инъекция в изображении | Модель выполняет текст с фото | Иерархия инструкций, изоляция, проверка действий |
| Слишком много вопросов | Падение конверсии | Максимум 3 вопроса, defaults, быстрый путь |
| Зависимость от host | Качество скачет между Claude/ChatGPT/Cursor | Строгая схема, skill, eval на 3 host, понятные ошибки |
| Host не вызывает tools | Агент отвечает «из головы» | Один высокий `plan_trip`, сильные описания tools, prompts, smoke test |
| Рост `data/` | Диск заполняется | TTL, лимиты, очистка, метрика размера |
| Блокировки SQLite | Ошибки при конкурентной записи | WAL, один процесс, низкий трафик; Postgres при масштабе |
| Потеря данных | Удаление `./data` | Бэкапы, документация, `docker compose down` не удаляет volume |

## 18. Roadmap

Команда-минимум: 1 full-stack/ML-инженер + 1 backend/ML-инженер, продуктовый дизайн на part-time.

| Неделя | Фокус | Результат |
|---|---|---|
| 1 | Схемы, SQLite, 20 направлений, 3 core tools (`plan_trip`, `build_itinerary`, `validate_itinerary`), skill | Локальный MCP-сервер, первые 3 сценария |
| 2 | 50 направлений, `get_destination`/`verify_place`/`export`, Docker Compose | `docker compose up`, первые evals |
| 3 | HTTP, лимиты, 3 host, бета | 10 пользователей, логи, исправления tool descriptions |
| 4 | Документация, запуск, обратная связь | Публичный MVP, метрики, обратная связь |

**Критерий выхода в бету:**

- 30–50 реальных изображений из golden set проходят без критичных ошибок;
- 3 host проходят одинаковый smoke test;
- маршруты выполнимы в 95% проверок;
- пользователи в слепом тесте предпочитают планы агента шаблонным;
- стоимость внешних API и задержка укладываются в бюджет;
- есть понятный сценарий отказа при неопределённости.

Если разработчик один — реалистичный срок 6–8 недель. Если нужен только концепт-прототип без живых API — 1–2 недели.

## 22. Возможная монетизация

- **Open-source локальный MCP-сервер + skill:** бесплатно, как канал распространения.
- **Платный hosted MCP:** always-on, без Docker, OAuth, сохранённые поездки, премиум-данные.
- **Freemium:** короткий план бесплатно, детальный маршрут и PDF — по подписке/разово.
- **Партнёрские ссылки:** перелёты, жильё, экскурсии, страховка.
- **Premium:** несколько вариантов, live-проверка, консьерж, правки.
- **B2B:** white-label для туристических офисов, отелей и агентств.

В agent-native сценарии токены host-агента оплачивает пользователь или платформа. Наши затраты — хостинг, внешние API и данные. В собственном веб-приложении токены оплачиваем мы, поэтому там нужна отдельная экономика.

Главное — не превращать выдачу в рекламную свалку: доверие к рекомендациям и есть основной актив продукта.

## Итог

Image2Travel — это не «поиск по картинке», а **агент перевода визуального впечатления в выполнимое путешествие**. Его сила — в трёх вещах:

1. **Декомпозиция впечатления** на проверяемые элементы.
2. **Гибридный подбор** мест с честными альтернативами.
3. **Проверяемый маршрут**, где логистика, сезон и бюджет важнее красивых слов.

Технически MVP — это:

- **skill** с workflow и политикой честности;
- **MCP-сервер** на 6 tools;
- **SQLite** как единственная БД;
- **локальные файлы** в `data/files/`;
- **Docker Compose**, который запускается одной командой;
- **текстовый интерфейс** host-агента;
- **MCP App, PDF, OAuth и веб-приложение** — в next steps.

MVP должен доказать одну вещь: пользователь видит фото, получает план и думает: «Да, именно этого я и хотел. И я могу это сделать».
